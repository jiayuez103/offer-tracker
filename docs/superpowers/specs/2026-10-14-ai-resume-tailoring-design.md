# AI 按 JD 改简历（M4）设计

> 续 `2026-09-20-job-tracker-design.md`。本文只写这个功能改了什么。

## 1. 要解决的问题

每投一个岗位都要对着 JD 调简历：强调哪段经历、换哪些关键词、哪条 bullet 要重写。现在全靠手动比对，而 Tracker 其实已经存着两份必需的原料 —— 每条投递的 **JD 全文快照**（`data/jd/<appId>.md`）和档案里**结构化的经历条目**（`profile.json` 的 education / work / projects / activities）。

M4 做两件事：**按 JD 出一份匹配诊断**，以及**一个带上下文的对话框**，让用户能继续要求改写。

不做（留给 M5）：结构化简历编辑器、排版模板、导出 PDF、把改写结果写回档案。

## 2. 模型接入

用户自己配服务，不绑定任何一家。支持两种请求格式，覆盖绝大多数服务：

| 格式 | 覆盖 |
|---|---|
| `openai`（OpenAI 兼容） | DeepSeek、智谱、月之暗面、OpenRouter，以及本地 Ollama / LM Studio / vLLM |
| `anthropic` | Claude API |

`settings.ai`：

```json
{ "format": "openai", "baseUrl": "https://api.deepseek.com", "model": "deepseek-chat",
  "apiKey": "<只存在本机>", "forbidden": ["不能出现的说法"], "enabled": true }
```

**密钥纪律**：

- `apiKey` 只存在 `data/settings.json`（已被 git 忽略），**只在服务端读取**
- `GET /api/state`、`GET /api/settings` 返回时把 `apiKey` 换成 `hasKey: true|false`，网页永远拿不到原值
- 网页提交设置时，`apiKey` 为空字符串表示「不修改」，要清空得显式传 `null`
- 日志和报错里不得出现 key

**接口**：

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/ai/test` | 用当前配置发一句最短的请求，验证连通性和模型名 |
| POST | `/api/ai/diagnose` | `{appId, force}` → 匹配诊断（带缓存） |
| POST | `/api/ai/chat` | `{appId, message}` → 流式回复（SSE） |

错误要说人话，至少区分：没配置、401/403（key 不对）、402/余额不足、404（模型名不对）、连不上（本地服务没启动）、超时（默认 60 秒）。

## 3. 发出去的内容做减法

组装请求时只带**改简历用得着的**字段：姓名（中英）、求职意向、教育、实习 / 工作、项目、校园经历、技能、语言、自我评价。

**一律不发**：手机号、邮箱、微信、生日、民族、政治面貌、籍贯、身份证件信息、账号。这条在 `shared/aiprompt.js` 里用白名单实现，并有单测守着。

## 4. 匹配诊断

输入：JD 快照全文（截断到 8000 字）+ 裁剪后的档案 + 岗位名。要求模型只返回 JSON：

```json
{
  "summary": "一句话总体判断",
  "requirements": [{ "text": "JD 的要求", "match": "strong|partial|missing", "evidence": "对得上的经历，missing 时为空" }],
  "keywords": ["JD 里反复出现、档案里没有的词"],
  "rewrites": [{ "target": "work_xxx", "original": "原 bullet", "rewrite": "改后", "why": "为什么这么改" }]
}
```

**容错**：模型不一定严格返回 JSON。解析顺序是「整体 JSON → 去掉 ```json 围栏 → 取第一个平衡的 `{...}`」；都失败就把原文当普通回复显示，不报错崩掉。字段缺失按空处理，`target` 对不上档案里任何一条的 `rewrites` 直接丢弃。

**缓存**：结果存 `data/ai/<appId>.json`，含模型名、时间、JD 快照的长度与哈希、诊断结果、对话记录（最多 40 条）。打开时有缓存就直接显示，并标注「基于 X 月 X 日的 JD」；JD 变了或点「重新诊断」才再花钱。

## 5. 对话

诊断下方是对话框，上下文 = 裁剪后的档案 + JD + 诊断摘要 + 最近若干轮对话。服务端用 SSE 往浏览器推增量文本（两种格式各自解析自己的流）。对话记录存在上面那个缓存文件里，下次打开还在。

## 6. 防编造（硬约束）

- 系统提示写明：**只能改措辞、顺序和侧重；不得新增没发生过的事实、公司、职称、时间；数字只能沿用原文，不得新造或放大**
- `settings.ai.forbidden` 是用户维护的「禁止出现的内容」清单，每次请求都附在系统提示里
- 每条改写建议必须带 `target`（对应档案条目 id），否则丢弃
- 界面上所有改写都是**建议**：可以复制，不会自动写回档案

## 7. 界面

- **设置页**新增「AI 服务」卡片：格式、地址、模型、API key（`type=password`，已配置时显示「已保存」）、禁止清单、「测试连接」按钮
- **投递抽屉**新增「AI」标签页：顶部是诊断（要求对照表 + 关键词缺口 + 改写卡片，每张可复制），下方是对话框。没配置 AI 时显示一句引导去设置页
- 没有 JD 快照时提示「先在这条投递里存一份 JD」

## 8. 测试

- `shared/aiprompt.js`：白名单裁剪（断言手机号 / 邮箱 / 微信不出现）、禁止清单进了系统提示、JD 截断
- `shared/llm.js`：两种格式的请求体构造、SSE 增量解析、JSON 容错解析（纯 JSON / 带围栏 / 夹在文字中间 / 完全不是 JSON）
- 服务端路由：用假 fetch 测成功、401、超时、未配置；断言响应里不含 key
- 端到端：用户在设置页填入真实 DeepSeek key 后，跑一次诊断和一轮对话

## 9. 成本与边界

- 一次诊断约几千 token，DeepSeek 下不到一毛钱；对话按需
- 响应里带 usage 时在界面上显示本次 token 数
- 超时 60 秒，失败不写缓存
